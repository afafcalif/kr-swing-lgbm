## 2. 대표 사례

### 2-1. 장 마감 후 계산 11분 동안 하트비트 정지

- **문제:** 모의 1일차(10-26) 장 마감 후 요약 단계가 약 11분 걸렸고, 그동안 하트비트가 끊겼다.
- **발견 경로:** 서브 PC 첫날 운영 기록(요약 단계 소요 시간과 하트비트 공백). 하트비트는 감시 작업이 상주 프로그램이 살아 있는지 보는 신호라, 끊기면 실제로 멈춘 것과 구별되지 않는다.
- **원인:** 요약 단계가 주 반복 안에서 15:30 1분봉을 계산 대상 전 종목(약 2,650종목)에 종목마다 한 번씩 받고(1초 5회 제한으로 약 9분), 15:30 기준 상위 3·15:20 측정·동결 코드 대조까지 차례로 기다렸다. 하트비트는 주 반복이 1분마다 찍고 있었다.
- **해결:** 하트비트를 별도 스레드로 옮기고 줄 끝에 "주 반복이 마지막으로 돈 뒤 지난 초"를 붙여, 감시 작업이 하트비트는 살아 있어도 주 반복이 5분 넘게 멈추면 따로 알린다. 무거운 계산은 15:32 부터 백그라운드 스레드에서 돌고(결과만 넘김), 정산·보유 갱신은 기다리지 않는다. 확인 리뷰 2회로 날짜·세대가 다른 계산 결과는 버리고, 16:20 상한을 넘기면 "대조 미완료"로 기록하며, 계산 프로세스 정리도 주 반복 밖에서 하도록 보완했다.
- **재현 시험:** `test_mock1.py` — 무거운 계산 중에도 주 반복이 바로 돌아오고 정산은 끝남, 하트비트 스레드 1분 한 줄, 주 반복 멈춤 알림 한 번, 계산이 다음 날까지 남으면 결과 버림, 정리 중인 프로세스가 안 꺼져도 09:00 손절 감시 지연 없음.

### 2-2. 매도 로직: 반복 수정에서 단순화로

- **문제:** 손절·추세 매도를 "팔릴 때까지" 다시 보내게 바꾼 뒤(넓은 리뷰 1차), 일부만 팔린 남은 수량을 어떻게 셀지가 확인 리뷰마다 다시 지적됐다.
- **발견 경로:** 넓은 리뷰 1차 뒤 Codex 확인 리뷰가 연달아 지적. 종목 단위로 남은 수량을 붙이자 같은 날 다시 산 새 거래까지 팔 수 있었고(N1 ~ N4), 거래(trade_id) 단위로 다시 설계하자 이번에는 값들이 엇갈리는 순간이 문제가 됐다.
- **원인:** 남은 수량 = 보유 파일 수량 − 체결 확인 수량 − 걸린 매도. 세 값이 서로 다른 시각에 바뀐다(보유 파일은 15:40 에 계좌로 바뀌고, 체결 조회는 늦거나 실패하고, 걸린 매도는 15:35 확인 전후로 뜻이 바뀜). 하나만 늦어도 의무가 잘못 끝나거나 판단을 미뤄야 했다.
- **해결:** 계산을 걷어내고 증권사 잔고를 정답으로 썼다. 의무는 종목 단위 표시 하나, 매 분 계좌의 매도 가능 수량(걸린 주문을 이미 뺀 값)만큼 시장가, 끝은 성공한 계좌 조회에서 보유 0 일 때만(일시 누락에 속지 않게 1분 넘는 간격으로 두 번 연속). 의무가 남은 종목은 다시 사지 않는다. 운영 코드가 약 70줄 줄었다(+262 / −333).
- **재현 시험:** `test_broad3.py`(다시 씀)·`test_broad4.py` — 계좌 조회 연속 실패 중 걸린 매도가 있으면 안 보냄, 매도 가능 수량 초과는 거부 뒤 다음 분, 15:40 뒤 늦게 끝난 15:35 확인에도 목록 유지, 계좌 응답에서 한 번 빠진 종목은 의무 유지. 가짜 서버도 증권사처럼 매도 가능 수량을 넘는 매도를 거부하게 바꿨다.

### 2-3. 지수 결측일 때 시장 필터가 "통과"

- **문제:** 전날 코스피 종가나 120일선이 결측이면 시장 필터(코스피 종가 ≥ 120일선일 때만 신규 매수)가 통과로 판정될 수 있었다.
- **발견 경로:** 넓은 리뷰 2차 반영분의 Codex 확인 리뷰.
- **원인:** 필터를 `not (종가 < 120일선)` 으로 계산했다. NaN 과의 비교는 항상 거짓이라 `not` 이 참이 된다.
- **해결:** 입력 확인을 먼저 한다: 종가·120일선이 유한한 양수, 최근 120일 종가에 결측·0 없음, 종가 / 120일선이 0.5 ~ 2.0. 아니면 필터 미통과 + 그날 신규 매수 없음(점검용 매수도 없음) + 알림. 실시간·장 마감 후 재계산·동결 코드 대조가 같은 함수를 써서 결과가 같다.
- **재현 시험:** `test_broad7.py` — 지수 NaN·0 이면 통과 아님, 예전 NaN 기록도 다시 확인, 15:18 주문 계획에 NaN 필터면 매수 없음·점검 모드 종료 안 함.

### 2-4. 응답 유실(UNKNOWN) 주문의 다음 날 복구

- **문제:** 주문을 보냈는데 응답이 사라지면 접수됐는지 알 수 없다. 다시 보내면 두 번 사고, 안 보내면 산 것을 모른다.
- **발견 경로:** GPT 리뷰(의도 선기록)로 틀을 만들고, Codex 확인 리뷰 3회가 복구 쪽을 차례로 지적했다(여러 날 꺼져 있던 경우, 대조 기준, 같은 종목 UNKNOWN 둘 이상).
- **원인:** 처음 복구는 직전 거래일 하나만 봤고, 대조 기준이 이미 갱신된 보유 장부여서 체결 여부를 잘못 판단할 수 있었다.
- **해결:** 보내기 직전 의도를 디스크에 쓰고 응답 없음은 UNKNOWN(다시 보내지 않음). 의도마다 주문 직전 보유 수량을 저장해 다음 날 "지금 계좌 수량 − 주문 직전 수량"으로 확정한다. 마지막 정산 완료일 이후 모든 거래일(최대 30)과 최근 5거래일을 차례로 대조한다. 같은 종목에 UNKNOWN 이 둘 이상이거나 체결 수량을 모르면 추측하지 않고 미확정(수량은 계좌, 손절가는 후보 중 높은 쪽, 신규 매수 차단, 알림).
- **재현 시험:** `test_safety.py`(전송 직후 강제 종료 → 재시작해도 재주문 없음), `test_confirm.py`(실행 안 한 날이 낀 복구), `test_second.py`(주문 직전 수량 기준), `test_third.py`(같은 종목 매도·매수 둘 다 UNKNOWN → 미확정 유지).

### 2-5. 현금 대조로 모의투자 수수료 0.35% 발견

- **문제:** 15:40 정산의 현금 대조(기대 현금 vs 증권사 D+2 예수금)가 모의투자에서는 매매가 있는 날마다 어긋나는 구조였다.
- **발견 경로:** Codex 리뷰(20번)로 넣은 현금 대조에서 드러났고, 넓은 리뷰 2차(11번)로 반영했다.
- **원인:** 기대 현금 계산이 백테스트와 같은 수수료 0.015% 를 늘 썼다. 키움 모의투자의 매매 수수료는 0.35% 다.
- **해결:** 수수료를 환경별 설정으로 분리(모의 0.35%, 실전 0.015%)하고 현금 대조는 그 환경 수수료로 한다. 정산 기록에는 "실전 수수료였다면"의 값을 함께 남겨 모의 결과를 실전 기준으로 읽을 수 있게 했다. 백테스트와의 차이는 EXEC_SPEC 12장 "알려진 차이"에 올렸다.
- **재현 시험:** `test_broad6.py` — 모의 수수료로 현금 대조가 맞음, 실전 수수료 기준 값 기록. 가짜 서버에 수수료율 인자를 넣어 앞 시험(`test_codex` 20)도 0.35% 로 고쳤다.
