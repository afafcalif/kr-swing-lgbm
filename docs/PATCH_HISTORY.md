## 2. 대표 사례

### 2-1. 장 마감 후 계산 11분 동안 하트비트 정지

- **문제:** 모의 1일차(10-26) 장 마감 후 요약 단계가 약 11분 걸렸고, 그동안 하트비트가 끊겼다.
- **발견 경로:** 서브 PC 첫날 운영 기록(요약 단계 소요 시간과 하트비트 공백). 하트비트는 감시 작업이 상주 프로그램이 살아 있는지 보는 신호라, 끊기면 실제로 멈춘 것과 구별되지 않는다.
- **원인:** 요약 단계가 주 반복 안에서 15:30 1분봉을 계산 대상 전 종목(약 2,650종목)에 종목마다 한 번씩 받고(1초 5회 제한으로 약 9분), 15:30 기준 상위 3·15:20 측정·동결 코드 대조까지 차례로 기다렸다. 하트비트는 주 반복이 1분마다 찍고 있었다.
- **해결:** 하트비트를 별도 스레드로 옮기고 줄 끝에 "주 반복이 마지막으로 돈 뒤 지난 초"를 붙여, 감시 작업이 하트비트는 살아 있어도 주 반복이 5분 넘게 멈추면 따로 알린다. 무거운 계산은 15:32 부터 백그라운드 스레드에서 돌고(결과만 넘김), 정산·보유 갱신은 기다리지 않는다. 확인 리뷰 2회로 날짜·세대가 다른 계산 결과는 버리고, 16:20 상한을 넘기면 "대조 미완료"로 기록하며, 계산 프로세스 정리도 주 반복 밖에서 하도록 보완했다.
- **재현 시험:** `test_mock1.py` — 무거운 계산 중에도 주 반복이 바로 돌아오고 정산은 끝남, 하트비트 스레드 1분 한 줄, 주 반복 멈춤 알림 한 번, 계산이 다음 날까지 남으면 결과 버림, 정리 중인 프로세스가 안 꺼져도 09:00 손절 감시 지연 없음.

### 2-2. 매도 로직: 반복 수정에서 단순화로

- **문제:** 손절·추세 매도를 "팔릴 때까지" 다시 보내게 바꾼 뒤(넓은 리뷰 1차), 일부만 팔린 남은 수량을 어떻게 셀지가 확인 리뷰마다 다시 지적됐다.
- **발견 경로:** 넓은 리뷰 1차 뒤 Codex 확인 리뷰가 연달아 지적. 종목 단위로 남은 수량을 붙이자 같은 날 다시 산 새 거래까지 팔 수 있었고(N1 ~ N4), 거래(trade_id) 단위로 다시 설계하자 이번에는 값들이 엇갈리는 순간이 문제가 됐다.
- **원인:** 남은 수량 = 보유 파일 수량 − 체결 확인 수량 − 걸린 매도. 세 값이 서로 다른 시각에 바뀐다(보유 파일은 15:40 에 계좌로 바뀌고, 체결 조회는 늦거나 실패하고, 걸린 매도는 15:35 확인 전후로 뜻이 바뀜). 하나만 늦어도 의무가 잘못 끝나거나 판단을 미뤄야 했다.
- **해결:** 계산을 걷어내고 증권사 잔고를 정답으로 썼다. 의무는 종목 단위 표시 하나, 매 분 계좌의 매도 가능 수량(걸린 주문을 이미 뺀 값)만큼 시장가, 끝은 성공한 계좌 조회에서 보유 0 일 때만(일시 누락에 속지 않게 1분 넘는 간격으로 두 번 연속). 의무가 남은 종목은 다시 사지 않는다. 운영 코드가 약 70줄 줄었다(+262 / −333).
- **재현 시험:** `test_broad3.py`(다시 씀)·`test_broad4.py` — 계좌 조회 연속 실패 중 걸린 매도가 있으면 안 보냄, 매도 가능 수량 초과는 거부 뒤 다음 분, 15:40 뒤 늦게 끝난 15:35 확인에도 목록 유지, 계좌 응답에서 한 번 빠진 종목은 의무 유지. 가짜 서버도 증권사처럼 매도 가능 수량을 넘는 매도를 거부하게 바꿨다.
- **이어서 — 분할 자동 조정 제거 (10-27 저녁):** 넓은 리뷰 2차 반영에서 체결로 설명되지 않는 보유 수량 변화를 액면분할·병합으로 보고 손절가·진입가를 정수 비로 자동 조정하게 했다. 확인 리뷰 2회가 그 조정을 아침 복구·공식 재판단·UNKNOWN 처리 경로마다 지켜야 하는 데서 빠진 곳을 계속 찾았고, 판단이 틀리면(사람이 직접 매매, 15:40 갱신 도중 꺼짐) 손절가가 틀린 값이 된다. 같은 방식으로 조정 코드를 지우고, 그 종목만 수동 확인(손절가 그대로, 자동 손절·추세 매도·신규 매수 멈춤, 알림, 다른 종목은 그대로)으로 바꿨다. 재현 시험 `test_broad9.py`.

### 2-3. 지수 결측일 때 시장 필터가 "통과"

- **문제:** 전날 코스피 종가나 120일선이 결측이면 시장 필터(코스피 종가 ≥ 120일선일 때만 신규 매수)가 통과로 판정될 수 있었다.
- **발견 경로:** 넓은 리뷰 2차 반영분의 Codex 확인 리뷰.
- **원인:** 필터를 `not (종가 < 120일선)` 으로 계산했다. NaN 과의 비교는 항상 거짓이라 `not` 이 참이 된다.
- **해결:** 입력 확인을 먼저 한다: 종가·120일선이 유한한 양수, 최근 120일 종가에 결측·0 없음, 종가 / 120일선이 0.5 ~ 2.0. 아니면 필터 미통과 + 그날 신규 매수 없음(점검용 매수도 없음) + 알림. 실시간·장 마감 후 재계산·동결 코드 대조가 같은 함수를 써서 결과가 같다.
- **재현 시험:** `test_broad7.py` — 지수 NaN·0 이면 통과 아님, 예전 NaN 기록도 다시 확인, 15:18 주문 계획에 NaN 필터면 매수 없음·점검 모드 종료 안 함.

### 2-4. 응답 유실(UNKNOWN) 주문의 다음 날 복구

- **문제:** 주문을 보냈는데 응답이 사라지면 접수됐는지 알 수 없다. 다시 보내면 두 번 사고, 안 보내면 산 것을 모른다.
- **발견 경로:** GPT 리뷰(의도 선기록)로 틀을 만들고, Codex 확인 리뷰 3회가 복구 쪽을 차례로 지적했다(여러 날 꺼져 있던 경우, 대조 기준, 같은 종목 UNKNOWN 둘 이상).
- **원인:** 처음 복구는 직전 거래일 하나만 봤고, 대조 기준이 이미 갱신된 보유 장부여서 체결 여부를 잘못 판단할 수 있었다.
- **해결:** 보내기 직전 의도를 디스크에 쓰고 응답 없음은 UNKNOWN(다시 보내지 않음). 의도마다 주문 직전 보유 수량을 저장해 다음 날 "지금 계좌 수량 − 주문 직전 수량"으로 확정한다. 마지막 정산 완료일 이후 모든 거래일(최대 30)과 최근 5거래일을 차례로 대조한다. 같은 종목에 UNKNOWN 이 둘 이상이거나 체결 수량을 모르면 추측하지 않고 미확정(수량은 계좌, 손절가는 후보 중 높은 쪽, 신규 매수 차단, 알림).
- **재현 시험:** `test_safety.py`(전송 직후 강제 종료 → 재시작해도 재주문 없음), `test_confirm.py`(실행 안 한 날이 낀 복구), `test_second.py`(주문 직전 수량 기준), `test_third.py`(같은 종목 매도·매수 둘 다 UNKNOWN → 미확정 유지).

### 2-5. 현금 대조로 모의투자 수수료 0.35% 발견

- **문제:** 15:40 정산의 현금 대조(기대 현금 vs 증권사 D+2 예수금)가 모의투자에서는 매매가 있는 날마다 어긋나는 구조였다.
- **발견 경로:** Codex 리뷰(20번)로 넣은 현금 대조에서 드러났고, 넓은 리뷰 2차(11번)로 반영했다.
- **원인:** 기대 현금 계산이 백테스트와 같은 수수료 0.015% 를 늘 썼다. 키움 모의투자의 매매 수수료는 0.35% 다.
- **해결:** 수수료를 환경별 설정으로 분리(모의 0.35%, 실전 0.015%)하고 현금 대조는 그 환경 수수료로 한다. 정산 기록에는 "실전 수수료였다면"의 값을 함께 남겨 모의 결과를 실전 기준으로 읽을 수 있게 했다. 백테스트와의 차이는 EXEC_SPEC 12장 "알려진 차이"에 올렸다.
- **재현 시험:** `test_broad6.py` — 모의 수수료로 현금 대조가 맞음, 실전 수수료 기준 값 기록. 가짜 서버에 수수료율 인자를 넣어 앞 시험(`test_codex` 20)도 0.35% 로 고쳤다.

### 2-6. 갱신 안전장치가 운영에서 작동하며 찾은 설정 버그

- **문제:** 10-27 넓은 리뷰 2차 보완을 서브 PC 에 올리자 코드 갱신(`update.bat`)이 시험 실패로 이전 커밋으로 자동으로 되돌렸다.
- **발견 경로:** 갱신 안전장치(끄기 → pull → 동결 코드 확인 → 시험 전체 → 켜기, 시험이 실패하면 이전 커밋으로 되돌려 켬)가 운영에서 처음 작동했다. 되돌린 이유를 따라가 보니 시험만의 문제가 아니었다.
- **원인:** 실패한 시험(거래시간 변경일)이 서브 PC 의 `config.json` 에 없는 `times.stop_send_until` 키에서 멈췄다. 이 키는 넓은 리뷰 1차(15:29 동시호가 매도)에서 `config.example.json` 에만 넣었고, 서브 PC 의 설정 파일은 그 전에 만든 것이었다. 실제 실행에서도 시각표에 없는 키는 코드 기본값(15:29)으로 쓰여 거래시간 변경일 이동에서 빠진다. 그대로 두었으면 11-19 수능일(폐장 16:30)에 손절 매도 마감이 15:29 로 남는 실제 버그였다.
- **해결:** 설정 깊은 병합: `config.example.json` 을 기본값으로 깔고 PC 별 `config.json` 을 하위 항목까지 키 단위로 덮어쓰며, 기본값으로 채운 키는 시작 때 로그에 남긴다. 시각 이동은 병합된 전체 시각표에 적용한다. 시험은 환경 변수(`LIVE_CONFIG=example`)로 PC 의 설정 파일을 읽지 않게 하고, 그 변수가 설정된 채로는 상주·감시·갱신·제어 프로그램이 시작을 거부한다. 같은 안전장치가 느린 PC 에서 시간에 민감한 시험 때문에 멀쩡한 커밋을 되돌리지 않도록, 고정 시간 대기 시험을 조건 대기로 바꿨다.
- **재현 시험:** `test_broad8.py` — 키가 빠진 오래된 설정으로 수능일의 모든 시각 키가 이동, 채운 키 기록, 시험은 PC 설정을 읽지 않음. `test_broad9.py` — 시험용 환경 변수가 있으면 네 프로그램 모두 시작 거부. 전체 시험을 깨끗한 clone 과 서브 PC 처럼 키가 빠진 설정 파일을 둔 환경 양쪽에서 돌려 확인했다.

### 2-7. 외부 유량 규칙 변경 대응 (10-28)

- **문제:** 모의 3일차(10-28) 15:21 매수 주문 하나가 HTTP 429(호출 한도 초과)를 받았고, 1초 뒤 재시도로 접수됐다. 같은 날 키움이 유량 기준 공지 2건을 냈다: 모의는 계좌별 TR 1개당 초당 1회(주문·조회 모두), 실전은 주문·조회 각 초당 5회, 잔고 조회(kt00018)는 초당 3회로 축소.
- **발견 경로:** 운영 기록의 429 한 건과 공지. 고치기 전에 호출 경로부터 조사했다.
- **원인:** 호출 제한기가 여러 개였다. 주문·계좌 클라이언트에 하나, 시세는 쓰는 곳마다 따로(손절 감시, 15:18:30 스냅샷, 일봉 반영)라 같은 토큰에 합쳐서 한도를 넘을 수 있었다. 주문 간격은 보내는 쪽에서 1.0초였지만 네트워크 지연 차로 서버에는 1초 미만으로 닿았다. 그리고 429 를 거부로 세서, 매수·08:30 추세 매도는 두 번 걸리면 그 종목을 놓치는 구조였다.
- **해결:** 세 번에 걸쳐 닫았다.
  1. 프로세스 공용 제한기(TR 별 최소 간격, 환경별 설정). 주문 429·유량 초과 응답은 보내지 않음(NOT_SENT)으로 보고 간격을 두고 다시 보내며, 조회 유량 오류는 조회 실패(보유 0 으로 읽지 않음)로 처리했다.
  2. 확인 리뷰 1: 공용 제한기 뒤에서 클라이언트 제한기가 전송을 더 늦춰 **실제 전송 간격이 여전히 1.0초**(10-28 원인 그대로)였고, 429 다시 보내기가 15:25 마감 뒤에 나갈 수 있었고, 15:21 매수 전 계좌 조회 한 번 실패로 그날 매수가 없어졌다. → 대기 장치를 클라이언트 전송 바로 앞 하나로 합치고, 계좌 조회 일시 실패는 마감 전까지 매 분 다시 조회.
  3. 확인 리뷰 2: 두 스레드가 동시에 기다리면 뒤 호출이 앞 호출의 늦은 실제 전송을 못 봐 실제 간격이 0.05초까지 줄었고, 매수 마감이 15:25(429 다시·재조회)와 15:28(첫 전송·매 분 다시 보내기) 두 개라 반례가 계속 나왔다(15:24 에 429 다시 보내기를 다 쓰면 15:25:00 매 분 다시 보내기가 15:25:02 에 접수). → 같은 제한은 잠금을 잡은 채 기다리고 깬 뒤 다시 확인. 15:20 ~ 15:30 은 장 마감 동시호가라 15:30 전에 접수된 주문은 모두 종가에 체결되므로(백테스트 가정과 같음) 매수 마감을 15:28 전 하나로 통일했고, 확인 리뷰는 여기서 끝났다.
  - 수정 확인 방식: 지적마다 재현 시험을 먼저 쓰고, **그 시험이 이전 커밋에서 실패하고(실제 간격 1.0초, 0.05초 등) 지금 통과하는 것**으로 고쳐졌음을 확인했다(확인 리뷰 2 에서는 새·고친 시험 12개).
- **재현 시험:** `test_broad10.py` — 10-28 재현(매수 3건 1초 미만 → 429 → 거부 횟수 0·간격 두고 다시 → 3건 접수), 잔고 429 + 빈 목록 = 조회 실패·매도 의무 안 끝남. `test_broad11.py` — 실제 키움 클라이언트 경로 + 가짜 서버(TR 별 간격을 어기면 429)로 실제 전송 간격 ≥ 1.2초, 15:21 잔고 조회 실패 → 15:22 성공 → 매수. `test_broad12.py` — 실제 스레드 두 개 동시 대기에서 실제 간격 ≥ 0.25초, 429 가 계속돼도 15:28 전까지만 전송.

### 2-9. 운영 숫자에서 찾은 메모리 문제 (10-29)

- **문제:** 장 마감 후 계산이 겹치는 몇 분 동안 서브 PC 의 메모리 커밋이 램의 90% 를 넘을 수 있었다.
- **발견 경로:** 사용자가 서브 PC 의 메모리 사용량이 전날 4GB 대에서 5 ~ 7GB 로 오른 것을 보고 프로세스를 따라갔다. 08:04 공식 시세 반영 뒤 다시 적재한 점수 계산 작업 프로세스 12개가 각각 약 570MB, 합쳐 약 7GB 를 잡고 하루 내내 남아 있었다. **리뷰와 시험은 이것을 못 잡았다.** 시험은 결과 값만 보고, 리뷰는 코드의 논리를 봤다. 묶음을 하루 동안 두는 것 자체는 설계대로(15:18 점수·15:32 장 마감 후 계산·아침 장부 계산에 씀)라 코드만 봐서는 문제가 아니었다.
- **원인 (조사):** 작업 프로세스 메모리의 대부분은 일봉 데이터가 아니라 수치 라이브러리 OpenBLAS(numpy·scipy 에 각각 들어 있음)가 불러올 때 CPU 스레드마다 잡는 버퍼였다. 메인 PC 에서 같은 계산으로 재면 작업자 하나 1,210MB 가 스레드 1개 설정으로 250MB 가 됐다. 15:32 에는 동결 코드 대조(별도 프로세스)가 계산 묶음을 한 벌 더 띄워, 그동안 최대 커밋이 약 15GB(램 16GB 의 90% 넘음)였다. 코드를 다시 보니 예외 경로 세 곳(적재 뒤 장부 읽기 실패, 준비 스레드의 적재 뒤 실패, 날짜가 바뀔 때 돌고 있던 준비)에서 묶음이 닫히지 않고 상주 프로그램이 끝날 때까지 남을 수 있었고, 동결 대조의 임시 파일도 지워지지 않고 쌓이고 있었다(메인 PC 2.7GB).
- **해결:** OpenBLAS 스레드 1개(상주·엔진 맨 앞, 자식 프로세스가 물려받음), 작업자 수 설정(`pool_workers`, 기본 6), 예외 경로 세 곳에서 묶음 닫기, 정상 종료 때 임시 폴더 정리. 결과 값은 대상 전 종목의 특징 50열과 점수가 스레드 수·작업자 수·동결 경로 모든 조합에서 **차이 0** 임을 확인했다. 서브 PC 추정 최대는 약 4.3GB(램의 약 27%)다.
- **재현 시험:** `test_memcash.py` — 환경 변수 자식 상속, 작업자 수 설정·자름, 예외 경로마다 묶음 닫힘, 날짜 바뀜에 버린 준비가 끝날 때 묶음 닫고 공개 안 함, 임시 폴더 정리. 같은 파일의 현금 대조 절사 시험과 함께 15개 모두 이전 커밋에서 실패하는 것을 확인했다.

### 2-10. 첫 손절 뒤 판 종목을 다시 감지 (10-29)

- **문제:** 모의 운영 첫 손절은 설계대로 끝났다. 감지 1초 뒤 시장가 전량 매도가 접수돼 전량 체결됐고, 2분 뒤 계좌 보유 0 확인으로 매도 의무가 끝났다(체결은 손절가 대비 약 1.3% 낮게, 1분 간격 감시의 영향). 그런데 약 2시간 뒤 같은 종목이 다시 손절 대상으로 잡혀 "손절 진행 중" 표시와 알림이 나갔다. 주문은 나가지 않았다.
- **발견 경로:** 서브 PC 운영 기록과 알림.
- **원인:** 보유 파일은 15:40 장 마감 정산 때 계좌로 갱신된다. 손절 감시는 "계좌 조회가 됐는데 계좌에 없는 종목"만 감지에서 빼므로, 계좌 조회가 서버 오류(HTTP 502)로 실패한 분에는 보유 파일만 보고 이미 판 종목을 다시 감지했다. 주문이 안 나간 것은 오늘 그 종목에 접수된 매도가 있으면 보유 파일 수량으로 다시 팔지 않는 다른 안전장치 덕이었다. 그대로 두면 계좌 조회가 실패할 때마다 알림이 반복되고, 15:18 매수 계획에서 그 종목이 "매도 의무 남음"으로 잘못 빠질 수 있었다.
- **해결:** 의무가 끝날 때 보유 파일에 '오늘 판 종목' 표시를 남긴다. 표시된 종목은 15:40 갱신 전까지 새 손절 감지·15:18 매수 계획의 의무 판단·08:30 추세 매도 대상에서 빠지고, 성공한 계좌 조회에서 다시 보유로 보이면(같은 날 재매수 등) 표시를 지운다. 날짜가 다른 표시는 무효다.
- **재현 시험:** `test_closed.py` — 손절 → 체결 → 의무 끝 → 다음 분 계좌 502 에 의무·알림·주문 없음, 같은 상황에서 15:18 계획에 매수 대상으로 남음, 다시 보유면 표시 해제, 날짜가 바뀌면 무효, 15:40 뒤 표시 지움, 추세 매도 대상 아님. 앞의 두 시험이 이전 커밋에서 실패하는 것을 확인했다.

### 2-11. 한 종목 사정으로 하루를 버리지 않기 (10-30)

- **문제:** 07:00 일봉 갱신에서 키움이 일부 종목에 빈 응답을 줬다. 그중 몇 종목이 매수 대상 후보여서 "대상 후보 일봉 수집 실패 → 그날 신규 매수 안 함"이 걸렸고, 08:04 공식 시세 반영 뒤에도 풀리지 않아 그날 신규 매수가 없었다. 첫 Codex 리뷰(27번)에서 정한 규칙대로 작동한 것이다.
- **발견 경로 — 사용자 문제 제기:** "한 종목 때문에 하루를 버리면 그날이 중요한 날일 수 있다", "그 종목의 특이사항을 미리 알면 된다", "받은 시세가 수정주가면 이전 시세랑 섞인다". 하루 차단이라는 안전장치의 비용을 따져 보자는 지적이었다.
- **조사에서 찾은 더 큰 문제:** 기본 일봉 파일에 추가분만 붙이는 구조에서, 아침 대조로 권리락·분할·병합 때문에 수정주가 계수가 바뀐 것이 보이면 그 종목을 통째로 뺐다. 이 제외는 기본 파일을 손으로 다시 만들 때까지 끝나지 않았다. 서브 PC 에서 최소 12종목이 빠져 있었고 거래일마다 약 1종목씩 늘고 있었다. 실전 유니버스가 매일 줄어 백테스트와 달라지고 있었던 것이다. 빈 응답 자체는 HTTP 200 에 빈 목록이었고 응답 코드·메시지를 기록하지 않아 원인을 알 수 없었다(이번부터 남김).
- **근거를 먼저 확인:** 키움 원주가 파일의 계수 변화 643건(2025-03 ~ 2026-10)이 모두 한국거래소 공식 시세의 "기준가 ÷ 전날 종가"와 0.1% 안에서 일치했다(524건은 정확히 같음). 이전 이력에 이 비율을 곱하면 키움이 새로 준 이력과 모든 행이 0.17% 안이었고, 동결 특징 함수로 계산한 특징값 차이는 표준편차 0.04배 이하, 대상 여부가 바뀐 행은 0 이었다. 그래서 제외 대신 이력을 다시 맞추는 쪽으로 재설계했다. 원칙(사용자 결정): 데이터를 제대로 갖추는 게 먼저, 종목 제외는 마지막 수단, 하루 차단은 시장 전체 문제일 때만.
- **해결 — 첫 수정과 세 단계, 각각 Codex 확인:**
  - 첫 수정: 실패 원인 원문 기록, 갱신 끝에 다시 받기, 공식 값 채움. 확인 리뷰가 "채운 종목의 15:18 기준가가 다르면(그날 권리락 등) 수정 안 된 이력으로 점수가 계산될 수 있다"를 찾아, 그런 날은 매수하지 않게 했다.
  - 1단계: 그날 계수를 15:18 기준가로 정하고, 당일 실패는 그 종목만 제외(한 단계 실패가 5% 이상일 때만 하루 차단). 확인 리뷰가 **실패율 중복 집계**를 찾았다 — 같은 종목이 두 항목으로 남으면 40종목 중 1종목 실패가 2/40 = 5% 로 세어져 하루가 막혔다.
  - 2단계: 계수 바뀐 종목의 이력을 다시 맞춰 대상에 남기고, 장 마감 후 보유 판단과 보유 종목 손절가에도 그날 계수를 적용. 예전에는 보유 종목의 무상증자 권리락 날 가격이 기계적으로 떨어진 것만으로 장중 손절이 걸리는 경로가 있었다(백테스트는 수정주가 기준이라 안 팖). 확인 리뷰가 **채울 때 계수 승계 누락**(다시 맞춘 종목이 다음 날 수집 실패로 공식 값으로 채워지면 이벤트 전 이력과 새 기준 이력이 섞여, 분할 종목의 20일 수익률 +13.58% 가 −43.21% 로 읽혀 후보에서 빠짐)과 **이벤트 다음 날 손절가 복귀**(다음 날 아침 복구가 전날 조정을 풀어 현재가에 잘못 매도)를 찾았다.
  - 3단계: 장중 재수집, 공식 값 채움의 이벤트 날 계수, 데이터 버전 고정, 다음 날 대조. 확인 리뷰가 **늦은 재적재가 15:18 스냅샷을 막음**(15:12 시작·15:22 완료면 적재 중 표시 때문에 15:18:30 스냅샷이 "준비 안 됨"으로 실패해 그날 매수 누락 → 이중 적재로 기존 적재가 계속 돌게)과 **사용 중 버전 삭제**(재수집 버전이 여러 번 공개되면 아직 쓰는 아침 버전이 정리돼 15:32 동결 대조가 다른 버전으로 계산 → 불일치 차단 → 사용 중 표시로 보호)를 찾았다.
  - 확인 리뷰가 찾은 문제마다 **이전 커밋에서 실패하는 재현 시험**을 먼저 썼다. 1단계 보완 4개 모두, 2단계 보완 7개 중 6개, 3단계 보완 9개 중 8개가 이전 커밋에서 실패했다(나머지는 "멈추지 않음"·예전 기록 쪽이라 예전에도 통과하는 것이 맞음).
- **재현 시험:** `test_fetchfill.py`(다시 받기·공식 값 채움), `test_basefactor.py`(그날 계수·그 종목만 제외·아침 기준가 측정), `test_failshare.py`(실패율 집계), `test_rebase.py`(실제 과거 일봉 `testdata/` 로 이벤트 전 이력 × 기준가비 = 키움 새 이력, 이력 다시 맞추기, 보유 종목 손절가), `test_fix11r.py`(계수 승계·이벤트 다음 날 손절가), `test_intraday.py`(장중 재수집 → 차단 해제 → 정상 매수, 버전 고정, 다음 날 대조), `test_swap.py`(이중 적재·사용 중 버전).

## 4. 배운 점

- **덧대기보다 단순화:** 같은 곳이 리뷰마다 다시 지적되면 예외를 덧대지 않고 계산 자체를 걷어냈다(매도 의무는 증권사 잔고로, 분할은 자동 조정 제거로, 2-2; 매수 마감은 15:25·15:28 두 개를 15:28 하나로, 2-7).
- **애매하면 추측하지 않음:** 접수 여부·체결 수량·필터 입력을 모르면 짐작하지 않고 미확정이나 매수 없음으로 두고 알렸다(2-3, 2-4).
- **드문 일은 사람에게:** 분할 같은 드문 수량 변화나 갱신 시험 실패는 자동으로 맞히려 하지 않고 그 종목·그 갱신만 멈춰 사람에게 넘겼다(2-2, 2-6).
- **운영 숫자의 작은 변화를 본다:** 리뷰와 시험이 못 잡은 메모리 문제를 전날보다 조금 오른 메모리 사용량에서 찾았다(2-9).
- **안전장치의 비용도 따진다:** 한 종목 문제로 하루를 막는 대신 그 종목만, 그것도 데이터를 갖출 수 없을 때만 뺀다(2-11).
